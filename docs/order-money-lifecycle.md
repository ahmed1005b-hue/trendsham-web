# 🛒 دورة الشراء والمبالغ في Trendsham

> شرح شامل لرحلة الطلب: من شراء العميل ← الدفع ← الشحن ← العمولة ← سحب البائع لأرباحه،
> بالإضافة إلى علاقة العميل بطلبه بعد الشراء. مبني على قراءة الكود الفعلي للمشروع.

---

## 1️⃣ العميل يشتري (Checkout)

**الملف:** `app/Http/Controllers/Customer/CheckoutController@store`

كل شيء يحدث داخل **معاملة قاعدة بيانات (DB Transaction)** مع **قفل المخزون** حتى لا يبيع مشتريان آخر قطعة معاً:

1. التحقق من الكمية والسلة.
2. إنشاء الطلب برقم تلقائي بصيغة: `TS-YYYYMMDD-XXXXXX`.
3. حساب المبالغ:

```
total = المجموع الفرعي (subtotal) + أجرة الشحن − خصم الكوبون − خصم نقاط الولاء
```

> ⚠️ كل المبالغ في المشروع محفوظة **بالوحدة الصغرى (×100)** — أي القيم مخزنة بالقرش
> وتُعرض بالليرة بعد القسمة على 100.

4. **الكوبون — مَن يتحمّل الخصم؟**
   - كوبون **البائع** → يُخصم من أرباحه لاحقاً (`discount_funder = seller`).
   - كوبون **المنصة** → تتحمّله المنصة ولا يمس أرباح البائع إطلاقاً.
5. عند التأكيد يُنشأ:
   - سجل `Payment` بحالة `pending`.
   - سجل `Shipment` بحالة `pending`.
6. تُحذف السلة، ويصلك إشعار _"تم استلام طلبك"_ ويُنبَّه البائع (Push).

## 2️⃣ الدفع

**الملف:** `app/Services/PaymentService.php`

البوابة تُختار من متغير البيئة `PAYMENT_DRIVER`:

| القيمة    | المعنى                     |
| --------- | -------------------------- |
| `manual`  | دفع عند الاستلام (افتراضي) |
| `sandbox` | بوابة تجريبية              |
| `bank`    | بوابة بنك حقيقية           |

### سير الدفع بالبطاقة

1. يفتح العميل صفحة الدفع في البنك.
2. البنك يُعيد النتيجة عبر **Webhook** إلى `PaymentService::apply()`.
3. `apply()` تتحقق من **تطابق المبلغ** مع المتوقع، ثم تسجّل الدفعة `paid`
   وتحدّث `payment_status = paid` على الطلب.

### الحمايات المدمجة

| الحالة                | التصرف                                              |
| --------------------- | --------------------------------------------------- |
| دفعة مكررة لطلب مدفوع | تُسجَّل `duplicate` + إنذار فوري للإدارة لاسترجاعها |
| مبلغ غير مطابق        | تُرفض وتُسجَّل `failed` مع تحذير في اللوج           |
| دفعتان متزامنتان      | قفل صف الطلب يمنع تسجيله مدفوعاً مرتين              |

### البطاقات المحفوظة

يُدعم حفظ البطاقات (Token فقط، لا تُخزَّن أرقام) عبر `startCardSave` + `applyCard`،
مع دعم تعيين بطاقة افتراضية وحذفها.

## 3️⃣ الشحن والتسليم

- سجل `Shipment` يتبع الطلب (`order_id`, `seller_profile_id`, `shipping_company_id`, `tracking_number`, `status`).
- **البائع** (عبر `SellerOrderService`) يستطيع فقط:
  - تحريك الحالة **للأمام فقط**: `processing → shipped → delivered`.
  - الإلغاء **قبل الشحن فقط**.
  - لا يستطيع وضع `paid` — ذلك حكر على الدفع/الإدارة.
  - الطلب المشترك بين أكثر من متجر تديره **الإدارة فقط**.
- كل تغيير حالة يمر عبر `Order::changeStatus()` — **نقطة واحدة مقفولة** تمنع تنفيذ
  الأثر المالي/المخزني مرتين عند طلبين متزامنين، وتمنع إعادة فتح طلب ملغٍ.

### حالات الطلب (`Order::STATUS_LABELS`)

```
pending    → قيد المراجعة
paid       → مدفوع
processing → قيد التجهيز
shipped    → تم الشحن
delivered  → تم التسليم
cancelled  → ملغي
```

## 4️⃣ العمولة والمال — اللحظة الحاسمة

**الملفات:** `app/Models/Order.php` + `app/Models/OrderItem.php` + `app/Services/LedgerService.php`

تسوية مالية عند **أول وصول الطلب إلى `delivered`** فقط (`Order::settleForStatusChange` → `OrderItem::settleCommission`):

```
أساس التسوية   = سعر البند − خصم كوبون البائع (إن وُجد)
عمولة المنصة   = الأساس × نسبة العمولة
ربح البائع     = الأساس − العمولة
```

- **نسبة العمولة**: عامة من `PlatformSetting` (الافتراضي **10%**) أو **خاصة لكل بائع** (`commission_rate` في `SellerProfile`).
- بند هدية أو مغطّى بالكامل بكوبون البائع: **لا ربح ولا عمولة**.

### ما يحدث في نفس اللحظة

1. 💰 **محفظة البائع (Wallet)**: يُضاف بها `vendor_earning` (حركة `credit` نوعها `order_earning`).
2. 📒 **الدفتر المحاسبي (LedgerService)**: قيدان بنفس اللحظة:
   - `sale` (دائن) بكامل المبيعات.
   - `commission` (مدين) بقيمة العمولة.
   - المصدر `order_item + id` يضمن **عدم التكرار** (idempotent).
3. ✅ علم `commission_settled_at` يضمن عدم تسوية البند مرتين.
4. 🎁 نقاط الولاء تُكتسب للعميل (مرة واحدة لكل طلب).
5. 🚚 كوبون شحن مجاني من البائع: تُخصم أجرة الشحن عليه (`SellerShippingCharge`).

### عند الإلغاء / الاسترجاع (`reverseSettlement`)

- يُخصم ربح البائع من محفظته — **حتى لو صار الرصيد سالباً** (إن كان قد سحب سابقاً، لا يستطيع السحب مجدداً حتى يُغطّى العجز).
- قيود مبيعات + عمولة تُعكس (`refund` + `commission_reversal`).
- الكميات تعود للمخزون، الكوبون يعود لمحفظة العميل، النقاط تُعالج، وأجرة الشحن تعود للبائع.

## 5️⃣ كيف يأخذ البائع أمواله (Payout)

**الملف:** `app/Services/PayoutService.php`

### الخطوات

1. **طريقة استلام**: يضيف البائع بطاقة بنك / IBAN / محفظة إلكترونية.
   - تحقق تلقائي: **Luhn** لأرقام البطاقات و**خوارزمية IBAN** للحسابات.
   - تحتاج موافقة الإدارة (`is_verified`) قبل استخدامها (حسب الإعداد).
2. **طلب سحب**:
   ```
   المبلغ المتاح = رصيد المحفظة − مجموع طلبات السحب المعلّقة (pending)
   ```
   مع حد أدنى قابل للضبط (`payment.payout.min_amount`) وقفل المحفظة ضد الطلبات المتزامنة.
   تُنسخ بيانات التحويل **لحظة الطلب** فلا تتأثر لو عدّل البائع طريقته لاحقاً.
3. **موافقة الإدارة (`approve`)**:
   - يُخصم المبلغ من المحفظة **فوراً** (حركة `debit` نوعها `withdrawal`).
   - قيد محاسبي `payout` في الدفتر.
   - الحالة تصبح `approved`.
4. **التحويل**: تلقائياً عبر بوابة البنك (`BankPayoutGateway`) أو يدوياً من الإدارة،
   ثم `markPaid` برقم **حوالة إلزامي** وإيصال اختياري → الحالة `paid`.
5. **فشل الحوالة (`markFailed`)**: يُعاد المبلغ لمحفظة البائع **تلقائياً** + قيد عكسي `payout_reversal`.

### دورة حالة طلب السحب

```
pending ──approve──► approved ──► paid
   │                    │  ├─► processing ──► paid
   │                    │  └─► failed (يُعاد المبلغ للمحفظة)
   └─► rejected (بدون أي خصم)
```

### حالات فشل الاتصال بالبنك

إذا انقطع الاتصال أثناء الإرسال، يبقى الطلب `approved` ويمكن إعادة المحاولة —
**لا يُعاد المبلغ** لأننا لا نعرف إن كانت الحوالة نُفّذت فعلاً.

## 6️⃣ علاقة العميل بطلبه (دورة الحياة الكاملة)

### أثناء الطلب

- الطلب يُنشأ بحالة `pending` مع إشعار فوري.
- بطاقة → الطلب معلّق حتى يؤكد البنك، ثم إشعار _"تم استلام دفعتك"_.
- دفع عند الاستلام → يدخل مباشرة وينتظر مراجعة الإدارة.
- كل تغيير حالة يصله **إشعار**: _"حالة طلبك أصبحت: ..."_.

### 🔑 حق العميل الوحيد: الإلغاء — بشرط صارم

**الملف:** `app/Services/CustomerOrderCanceller.php`

> **العميل يُلغي طلبه فقط وهو في حالة `pending` (قيد المراجعة).**

بمجرد "قيد التجهيز" أو بعدها تظهر له:

> _"ما بقدر تلغي طلب دخل مرحلة التجهيز أو تجاوزها."_

عند الإلغاء يحدث تلقائياً (تحت القفل):

1. المنتجات تُعاد للمخزون (الكمية + اللون/المقاس).
2. الكوبون المستخدم يعود لمحفظة العميل، ونقاط الولاء المستبدلة تُستعاد.
3. الدفعة المعلّقة تُعلَّم `failed`.
4. إشعار: _"تم إلغاء طلبك #..."_.

### ⚠️ لا يوجد استرجاع مؤتمت بعد الاستلام

- لا يوجد أي مسار (Route) يتيح للعميل طلب **إرجاع/استرجاع** لطلب مُسلَّم —
  الموجود فقط صفحة **سياسة الاسترجاع** (`/refund-policy`) كمتن قانوني ثابت.
- منطق `reverseSettlement` موجود لكنه يعمل فقط عند **إلغاء الإدارة أو البائع** — ليس بطلب من العميل.
- إذا وصل الطلب وساء العميل: عليه التواصل مع الدعم، والاسترجاع يُنفَّذ يدوياً من الإدارة
  (تغيير الحالة إلى `cancelled` يعيد المال تلقائياً بفضل النظام المزدوج).

### بعد التسليم — ماذا يملك العميل؟

- ⭐ تقييم المنتج (Review) — فقط إذا كان الطلب `delivered` ولم يقيّمه سابقاً.
- ⭐ تقييم البائع (SellerReview) على نفس البند.
- 🎁 نقاط ولاء اكتسبتها من الطلب صارت في محفظته لاستخدامها بطلب قادم.

---

## 📌 الخلاصة في سطر واحد

> العميل يدفع للمنصة ← عند التسليم تُحسب عمولة المنصة ويُودَع صافي ربح البائع في محفظته ←
> البائع يطلب سحباً فتخصم الإدارة من المحفظة وتحوّل له عبر البنك،
> وكل خطوة محمية بأقفال وقيد محاسبي مزدوج (محفظة + دفتر) يمنع التكرار أو الفقد.
